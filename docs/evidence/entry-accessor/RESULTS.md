# Entry-point accessor spike: results

> A spike. Its code was deleted with `spikes/` at the start of M2; it is in git history at [`spikes/entry-accessor/`](https://github.com/sotsera/spar/tree/24f5db0942833047c81fa692908410596f3b8960/spikes/entry-accessor) (commit `24f5db0`), and this record and its `results/` moved here. Paths under `spikes/` below name that history.

Recorded 2026-11-15. Question (plan section 5, issue L): can Spar's generator, running in the app project, give the test host a way into the app's own `Program.cs` in the `Test` variant only, so a test writes `SparTestApp.StartAsync<Program>()` with nothing hand-written, under CoreCLR and NativeAOT, while Production keeps no trace of it? `spikes/test-host` used a hand-written accessor in the test project.

**Short answer: yes.**
- **What the generator emits.** In the `Test` variant it makes `Program` public and implements `Spar.ISparEntryPoint` (one `static abstract int Run(string[] args)`), calling the compiler's top-level method through an `[UnsafeAccessor]`. The method's name is read from `Compilation.GetEntryPoint`, not assumed.
- **The test writes `StartAsync<Program>()`:** 3 of 3 tests passed under CoreCLR and under NativeAOT (`xunit.v3.aot`, 0 warnings, 19 s publish), with no reflection.
- **Production has none of it:** `Program` stays internal, no interface, no accessor, no generated file. The published executable contains none of the names (`ISparEntryPoint`, `SparEntry`, `SparTestSession`). `Development` is the same.
- **A `Program.cs` in another shape fails the `Test` build** with a located error (void return, async, classic `Main`) and builds normally in `Development`.

## Environment

Windows 11 Pro 10.0.26320, SDK 11.0.100, `Microsoft.CodeAnalysis.CSharp` 5.9.0 (the repository's generator version), `xunit.v3` and `xunit.v3.aot` 4.0.3. Repository policy: warnings as errors, code style, trim and AOT analyzers on.

Generated in the `Test` variant (`obj/test/Debug/net11.0/generated/…/Spar.TestEntryPoint.g.cs`):

```csharp
// <auto-generated/> Spar, Test variant only.
#nullable enable
public partial class Program : global::Spar.ISparEntryPoint
{
    static int global::Spar.ISparEntryPoint.Run(string[] args) => SparEntry(null, args);

    [global::System.Runtime.CompilerServices.UnsafeAccessor(global::System.Runtime.CompilerServices.UnsafeAccessorKind.StaticMethod, Name = "<Main>$")]
    private static extern int SparEntry(Program? program, string[] args);
}
```

**Found on the way:**
- **`$(Configuration)` is still empty when a `Directory.Build.props` is read** unless it was passed on the command line. A variant mapping or a folder name built from it there silently uses the empty string. The spike reads it with a `Debug` fallback; Spar.Sdk's mapping must be placed where the value is known. This is M1a work (decision "D3: variant builds run in-proc").
- **A netstandard2.0 generator cannot use `record`** without an `IsExternalInit` stand-in (CS0518); the spike used a class.
- **Conditions on the project's own `TargetFramework` belong in a `.targets` file.** In props the value is still the root's `net11.0`, so turning on the AOT analyzer there broke the netstandard2.0 generator (NETSDK1210).

## The session hook: `AsyncLocal` or compile-time interception

Not spiked. The reasoning for the decision:
- **What interception would do:** the generator would rewrite the app's `SparApplication.Create(…)` call to a test-only method in the `Test` variant.
- **It would not remove the ambient lookup.** Several apps start at once in one test process, so that method still has to find *this* test's session, which is the `AsyncLocal` again (or a thread-static, which is worse with `await`).
- **What it would remove is already gone in Production:** the one `IsSupported` branch in `Create`, which the trimmer removes behind the feature switch (`spikes/test-host`, section 8).
- **Cost:** a second piece of generated code at every `Create` call site.

The `AsyncLocal` hook therefore stays; interception buys nothing measurable here.

## Not tested

- **A `Program` declared `internal partial` by the app** together with the generated `public partial` (expected: CS0262, conflicting accessibility). The generator could report its own diagnostic instead; not written.
- **`Program` in a namespace:** top-level statements always produce a global `Program`, so only the global form was built; the generator handles a namespace in its text.
- **The IDE:** whether Visual Studio and VS Code show SPIKE001/002 as you type, and whether IntelliSense in the test project sees `Program` as an `ISparEntryPoint` before a build. That is the D1 follow-up's design-time question.
- **Linux:** not run; nothing here is OS-specific, but it is unverified.
- **Package consumption:** the generator and `Spar.Entry` were project references, not packages.
