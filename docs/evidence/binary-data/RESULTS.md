# Binary data: `byte[]` on the bridge against the app's own origin

Spike for decision "M3's decide-first questions", item 5: how fast a page receives and sends binary data as a `byte[]` in a bridge message (padded base64 inside the message's JSON), against the same bytes fetched from the app's own origin, which is the path an opaque handle (`/_spar/blob/<id>`) would take. Run 2026-11-27. The spike's code (`BinaryData/`, `BinaryData.Tests/`) was removed once M3b built binary data; it is in git history at commit `091e701`, under `spikes/binary-data/`.

## Method

- `BinaryData/` is a Spar app built from source; `BinaryData.Tests/BenchTests.cs` starts it in its real window (the Window surface: WebView2 offscreen on Windows, WebKitGTK on a private Xvfb on Linux) and saves the page's report in `results/`.
- The page (`frontend/src/main.ts`) measures six sizes, 16 KB to 32 MB, five runs each, with `performance.now()`: `blobs.get(size)` (a `byte[]` result, decoded into a `Uint8Array`), `fetch` of a file of the same bytes from the page's origin read with `arrayBuffer()`, and `blobs.put(bytes)` (a `byte[]` request; the backend answers its length). The bridge's limits are raised (`MaxResultBytes` 96 MB, `MaxMessageBytes` 48 MB) so 32 MB fits as base64.
- The origin files are page assets embedded in the executable (generated by `vite.config.ts`, typed `.webp` because the hosts serve only known types and the packer stores incompressible data as is), served by the same host code a blob route would use: `WebResourceRequested` on WebView2, the scheme handler on WebKitGTK. Uploading through the origin was not measured: an app has no route to POST to.
- Windows 11, WebView2 158 (Edge 158). Linux: Spar's CI image (Ubuntu 24.04, WebKitGTK 2.52, software rendering) in Docker Desktop on the same machine.

## Results

Medians of five runs, milliseconds (throughput in MB/s in brackets):

| Size | Windows bridge | Windows origin | Windows upload | Linux bridge | Linux origin | Linux upload |
|---|---|---|---|---|---|---|
| 16 KB | 1.1 | 1.7 | 1.2 | 1 | 1 | 1 |
| 256 KB | 8.3 (30) | 3.6 (69) | 8.2 | 9 (28) | 2 (125) | 7 |
| 1 MB | 26.9 (37) | 7.8 (128) | 27.5 | 30 (33) | 3 (333) | 20 |
| 4 MB | 104 (38) | 24.8 (161) | 106 | 109 (37) | 11 (364) | 68 |
| 12 MB | 305 (39) | 70.7 (170) | 309 | 330 (36) | 31 (387) | 254 |
| 32 MB | 820 (39) | 184 (174) | 833 | 953 (34) | 119 (269) | 728 |

WebKitGTK's page timer has a 1 ms resolution, so its small sizes are rounded. Raw rows: `results/windows-20261126-230838.json`, `results/linux-20261126-231159.json`.

- **The bridge carries binary at about 35–39 MB/s on both hosts,** in both directions: base64 encoding, the JSON message, the host's string copy and the page's decoding. A 1 MB value costs about 30 ms, much of it on the page's main thread.
- **The origin is 4 to 5 times faster on Windows and about 10 times on Linux** from 1 MB up, and the page reads the bytes without decoding them.
- **Below about 64 KB the two are equal** (one to two milliseconds), so a small `byte[]` has no reason to move.
- **The default limits stop `byte[]` at about 12 MB** (a 16 MB result as base64), and a request at about 3 MB (4 MB), before this spike's raised limits.

## Found

- **A `byte[]` of 4 MB or more failed on the page** as `protocol` / `malformed`: the SDK's base64 check was one regular expression whose repeated group gave up on 5.6 million characters (`windows-20261126-230534.json`; the first run, `windows-20261126-230438.json`, failed before the error named its step). Fixed in `src/Spar.Client/src/wire.ts` with a loop and a 6 MB test (commit "SDK: a byte[] of several megabytes decodes"); pitfall in "Wire format and serialization".

## What it suggests for M3b

An opaque handle read from the app's own origin for large binary data (exports, files, images from the backend), and `byte[]` kept for small values: the bridge is fine up to some tens of kilobytes and costs about 30 ms per megabyte beyond. The handle needs a route of its own (`/_spar/blob/<id>`, one use, behind the bridge's origin, frame and token checks), its lifetime (tied to the call's document, released when read or after a timeout), and an upload direction, which this spike could not measure. The decision is the user's (item 5: "then decide from the numbers").
