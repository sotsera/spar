# Development loop

Part of the Spar design. [`docs/plan.md`](../plan.md) has the goal, the settled decisions, the open questions and the milestones, and lists every design file. Section numbers are global: "section 4" anywhere in the plan, the design files or `docs/decisions.md` means the heading of that number, wherever it lives.

## 4. Development loop

- **Debug embeds no bundle.** The app, desktop or loopback, starts or reuses the Vite dev server and serves the page from it. The desktop bridge stays in-process.
  - Vite records itself in `obj/spar-dev-server.json`. It is reused across backend restarts, ends with its launcher's standard input, and has a 60 s idle watchdog (as built: below, "As built").
  - Measured: Fast Refresh inside WebView2 in 39 ms; a contract change restarts in about 5.4–6.1 s with Vite reused.
- **Node at run time in Debug is accepted** (user decision).
  - Without Node, the app stops with a clear error saying how to install it, or how to use the Release bundle; `spar doctor` checks the Node version.
  - `-p:SparDevServer=false` makes Debug embed the bundle through the same code as Release. It has no hot reload, and shows startup, theme, CSP and headers exactly as users will see them.
  - **Debug can keep `https://app.localhost`** (verified by `spikes/desktop-origin`). The host fetches each request from Vite in-process, so Debug and Release share storage, CSP and secure-context behaviour.
    - Medians, direct against proxied: Fast Refresh 25 and 23 ms, state kept 5 of 5 times, CSS 5 and 9 ms, error overlay 8 and 9 ms; a full page load costs about 35 ms more (117 against 153 ms).
    - Vite's `server.hmr` must point the client at `ws://127.0.0.1:<port>`. With the defaults it tries `wss://app.localhost`, which leaks and gets no updates. The Debug CSP adds that WebSocket to `connect-src`.
    - **Decided (user, 2026-11-14): this is the Debug default.** Serving straight from Vite stays an option. Checked in M1d step 1: Vite's nonce under the strict CSP through the proxy (0 violations on both hosts), and the Linux path through the custom scheme (HMR from `spar://app` to `ws://127.0.0.1:<port>` works).
    - **What proxies:** the host itself, with no proxy server or extra package. On Windows a `WebResourceRequested` filter for `https://app.localhost/*` takes each request, the host fetches it from Vite's loopback URL with `HttpClient` and answers with `CreateWebResourceResponse` through a deferral. On Linux the `spar://app` scheme handler does the same and answers with a `WebKitURISchemeResponse`. The HMR WebSocket is not proxied: the page connects to `ws://127.0.0.1:<port>` directly. All of it is Development-variant code, absent from Production.
    - **Proxy requirements** (`spikes/desktop-origin/Origin.Win/Host.cs`): forward `Accept` and the `Sec-Fetch-*` headers, pass `Content-Type` through, never cache; complete each request through a deferral on the STA, so a slow Vite holds the request but not the pump; `HttpClient` with `UseProxy=false` and no automatic decompression. Each proxied request took 0.5–15.5 ms.
    - **For HTML, drop `If-None-Match` and `ETag`.** The spike's proxy forwards `If-None-Match` to Vite. `spikes/csp-navigation` showed that a 304 then keeps a page whose nonce no longer matches the new header (2 violations, page stuck), so that proxy code as written would bring the bug back.
    - **As built (M1d step 1; decision "Debug through the app's own origin (implementation record; choices for review)", `docs/evidence/m1d-dev-server.md`):** the core's `src/Spar/DevServer/`, behind the feature switch `Spar.DevServer.IsSupported` (on only in a Development build with a frontend and no `SparDevServer=false`, off and trimmed elsewhere), with each host's request path calling it: `PageServer` on Windows, `SchemeServer` on Linux.
      - **Where the page comes from, in order:** `SPAR_DEV_SERVER_URL` in the environment, then `SparDevServerUrl` from the build (a runtime configuration value), each used as it is with nothing started; the server `obj/spar-dev-server.json` records, when its Vite process is alive and `/__spar/dev-server` answers with its instance; otherwise a new one. An address must be plain `http` on 127.0.0.0/8, `[::1]` or `localhost` with nothing after the origin, or the window shows the error page that says why.
      - **Starting one:** `npm run dev` in `SparFrontendPath` (on Windows `cmd.exe /d /s /c "npm.cmd" run dev`), on a free port of 127.0.0.1 the app picks, with `SPAR_DEV_SERVER_FILE`, `_PORT`, `_INSTANCE` and `_IDLE_SECONDS` in its environment. The Spar Vite plugin (`devServer.ts`) then listens on 127.0.0.1 at that port with `strictPort`, sets `server.ws` (Vite 8's name for `server.hmr`'s socket settings) to `ws://127.0.0.1:<port>` and `html.cspNonce` to a placeholder, and once it listens writes the record (its real address, the instance, Vite's pid and start time) through a temporary file and a rename. Spar never reads the address from npm's or Vite's output. A server a developer runs with the plugin gets the same settings at the port its config names (5173 by default, `strictPort`), without the record.
      - **Lifetime:** the server never belongs to the app: no kill-on-exit, so a backend restart reuses it (checked in 25–29 ms). Its output goes to `obj/spar-dev-server.log`, which every run that uses it reads from its own start (a reused server's from the file's end), never to a pipe of the app's, which would break when the app ends. It ends with its standard input, which is the app's own when that is a pipe (an agent's or a tool's) and otherwise a pipe whose writing end the launched process holds itself, so a console or an IDE's null device never ends it (and its keyboard shortcuts never read the console); the plugin reads that input itself, since Vite 8 listens for its end without reading it. Otherwise the plugin's watchdog ends it after 60 s with no request and no HMR connection. Spar ends a server as a whole tree (Vite's process and those below it, and its own launcher) only when its record does not answer or on Retry, never at the app's exit.
      - **Requests:** the host reads the method, the address and `Accept` and `Sec-Fetch-*` on its UI thread, takes a deferral (Windows) or a reference on the request (Linux), and `DevServerProxy` fetches on the thread pool; the response is put on the request back on the UI thread. The proxy refuses methods other than GET and HEAD (405), never sends `/_spar/` paths to Vite (the host answers the violation reports first; its own `/_spar/dev-server/` routes serve the error page's style, script and Retry), appends the path to the server's origin and checks the result stays there, refuses Vite's redirects and encoded bodies (502), forwards no cookie and no conditional header, keeps Vite's status, body and `Content-Type`, and puts the host's own policy and headers on every response, worker scripts included, in place of Vite's (no `ETag`, `Cache-Control: no-store`).
      - **The Debug policy:** `PagePolicy` composed with the server's socket: `connect-src` adds `ws://127.0.0.1:<port>`, and every HTML response's nonce, fresh per response in place of the plugin's placeholder in its body, goes in `script-src` (Vite's inline preamble) and `style-src` (the styles Vite's client injects; not with `AllowInlineStyles()`). The host composes it, not the plugin, so a server without the plugin cannot loosen it: an HTML document without the placeholder is the error page that names `spar()`.
      - **When the server is not there:** a document request gets the Development error page (503) with what happened, the server's last 60 lines, and a Retry button (its script and style are files of the proxy's route, so the strict policy holds; Retry posts to the proxy, which tries again and answers when that try ends, then the page loads `/` again); anything else gets 502. A server that was ready and whose process ends takes the window to the error page within about a second (its pid is polled each second). The app keeps running, and Vite's lines go to `app.log` under `Spar.DevServer` and to standard output.
      - **Without Node:** before the window, when the app is to start the server, npm and Node are looked up on `PATH`; without them the app stops with the start-up message (`StartupProblemKind.Missing`, exit code 3) naming the Node.js download page and `-p:SparDevServer=false`.
      - **Measured** (the Notebook, which adds Tailwind's CSS rebuild to every edit): Fast Refresh, file write to the edited component's render, 36 ms median on WebView2 and 32 ms on WebKitGTK, state kept 5 of 5 on both; CSS, write to the updated stylesheet fetched, 47 ms on both; a reused server's page to `ui-ready` 595–663 ms from the process start on Windows.
- **Hot Reload signal (decided, user, 2026-11-14), Debug only:**
  - After each C# edit that Hot Reload applies, the host's `MetadataUpdateHandler` sends a `backend-updated` event to the open pages. It carries a revision number, the time and the names of the updated types.
  - The SDK offers `onBackendUpdate(handler)`, for example to refetch the current view's data. In Release it is a no-op that the bundler removes.
  - **A toast by default:** Spar's development overlay shows a small, dismissable toast for each update, such as "Backend updated: CopyJobsService (revision 3)". An app can turn it off or show its own from `onBackendUpdate`.
  - **Limits:**
    - The event can arrive after the patched code already ran once.
    - Rejected or failed edits are known only to `dotnet watch`, so they stay in its terminal.
    - Contract and DTO edits still restart the app, as before.
  - **As built (M1d step 3; decisions "M1d step 3's shape: dotnet watch and Hot Reload" and "dotnet watch and Hot Reload (implementation record; choices for review)", `docs/evidence/m1d-hot-reload.md`):**
    - **The handler:** `Spar.HotReload.BackendUpdates` in the core, named by `[assembly: MetadataUpdateHandler]`. Its `UpdateApplication(Type[]?)` runs on the runtime's Hot Reload thread after each applied update, numbers it (one revision count per process, since an update patches the whole process), names the updated types (a compiler-generated type, such as an async method's state machine, by the type it belongs to) and hands `{"revision":3,"time":"…","types":["Notebook.Pages.PagesService"]}` to every listening host. It does anything only when `Spar.Development.IsSupported` and `MetadataUpdater.IsSupported` (`DOTNET_MODIFIABLE_ASSEMBLIES=debug`, which `dotnet watch` and the IDEs set) are both true; a Production image has none of it (the boundary test's markers).
    - **The hosts:** `WebViewBridge` (Windows) and `ScriptBridge` (Linux) post each update to their UI thread and send `backend-updated` to the current document; the loopback run sends it to every open document. Each logs `Hot Reload applied revision N (types); sent to …` under `Spar.Host`.
    - **The page:** `onBackendUpdate(handler)` from `@spar/app/sdk` returns its unsubscribe function; the handlers run in the order added (one that throws is logged and the rest still run), then the development overlay's toast, unless `configureSpar({ backendUpdateToast: false })`. Everything is reached behind `import.meta.env?.DEV === true`, which Vite's development server makes true and `vite build` false, so a bundle Spar builds (Release, Test, and Debug with `SparDevServer=false`) carries none of it and `onBackendUpdate` does nothing there (the boundary test's page markers). The toast is a host element with an open shadow root that adopts a constructed stylesheet, its text set with `textContent`: no `<style>`, no `style` attribute, no HTML string, so the strict policy and Trusted Types hold. A toast stays 8 s, a click dismisses it, and at most three show.
    - **The restart rule:** in a Development build the generator adds `Spar.ContractShape.g.cs`, an enum `SparContractShape` with one member named from a hash of the generated contract code (`Spar.Contracts.g.cs`: the catalog with the fingerprint, the commands and their limits and the page security, the dispatch, the serializers). An edit that changes any of it renames the member, which Hot Reload refuses (`ENC0020: Renaming enum value … requires restarting the application`), so `dotnet watch` restarts with a full build (the TypeScript client regenerated) and an IDE reports the rude edit instead of patching. Without it, such edits were only `ENC0118` warnings ("Changing 'auto-property' might not have any effect until the application is restarted"), on which `dotnet watch --non-interactive` restarts but which a patch can otherwise carry, leaving the catalog's old values in place. A command's body changes no generated code and is patched as usual.
    - **Measured** (the Notebook): a method-body edit to the host's line 0.07–0.17 s after the save once `dotnet watch` is warm (0.7–2.7 s for the first of a session), to the toast or the page's own refetch within about 0.1 s more; a contract edit to the restarted app listening 9–15 s on Windows (5 s of it `dotnet watch` waiting for an app that cannot see its Ctrl+C, below) and 3.1–4.8 s on Linux.
- **Release and test variants embed the bundle.** Each variant has its own `obj`/`bin`.
- **Launch profiles:** `Desktop` (the default, first in `launchSettings.json`; user decision) and `Loopback`. If the desktop cannot start (no display), the app stops with a clear error suggesting `dotnet run -lp Loopback` and never falls back on its own; `spar doctor` reports the same. The loopback dev session keeps one port and token across restarts. An orchestrator such as Aspire may assign the port, token and dev-server URL through the environment.
  - **As built (M1d step 2; decisions "M1d step 2's shape: loopback in the development loop" and "Loopback in the development loop (implementation record; choices for review)", `docs/evidence/m1d-loopback.md`):**
    - **Selection:** the `Loopback` profile sets `SPAR_HOST=Loopback`; the generated `Run` asks `Spar.Loopback.SparLoopbackHost.Chosen()` before the desktop hosts. `Desktop` or unset is the window; any other value stops the app (exit 70). Only a Development build references `Spar.Loopback` (and the ASP.NET Core framework it runs on), added by Spar.Sdk at build time so the restore every variant shares never changes; a Production build has neither, nor the variable's name.
    - **One run:** the same folders and log as the desktop's Development run, the page from the development server through `DevServerProxy` (its policy and nonce) or, with `SparDevServer=false`, the packed page; no window and no UI thread. The address with its token goes to standard output and `app.log`. Ctrl+C, `SIGTERM` and `SIGQUIT` end it cleanly.
    - **The dev session:** `obj/spar-loopback.json` holds the port and token, owner-only (0600; on Windows an access list with the current user alone). Its last-write time is when a run last held it (at start, each minute, at exit). A run continues the session when it was held less than 4 hours ago, and otherwise starts a new one: same port, new token, and the browser opens (the system's handler, or `SPAR_LOOPBACK_BROWSER`: a command with `{url}`, or `none`). Only a new session opens the browser. `SPAR_LOOPBACK_PORT` and `SPAR_LOOPBACK_TOKEN` bypass the record and the browser. A port another program holds gives a new port and session; this app's own running copy stops the start.
    - **Restarts:** a dev session's channel names its backend's run (`X-Spar-Run`). When it ends, a document that had connected looks at `POST /_spar/session` with its token (250 ms, 500 ms, then each second, each 5 s after a minute) and reloads once when another run answers; the same run, a refused token or an unknown path stop the wait with a console line, and three automatic reloads in a row into documents that each lost their backend within 5 s stop the reloads. Calls in flight end `transport` / `lost` when the channel closes; nothing is resent.
    - **Measured** (the Notebook): the page reloaded 771 ms (Windows) and 891–906 ms (Linux) after the new run listened; 0 violations.
- **`dotnet watch`** does not mark its builds, so the build never tries to detect it. The runtime decision above makes detection unnecessary.
  - **How it restarts the app (SDK 11.0.100, M1d step 3):** it stops the running app first, on Linux with `SIGTERM`, which both Spar hosts answer with a clean exit, and on Windows with a Ctrl+C sent to `dotnet run`'s console. A Windows app built as `WinExe` (the Notebook, the template) has no console, so it never sees the Ctrl+C: `dotnet watch` waits 5 s (`DOTNET_WATCH_PROCESS_CLEANUP_TIMEOUT_MS`) and then ends the whole tree, the Vite server the app started included, so the next run starts a new one (about 0.8 s) and the page's Vite client reports its lost server once. Not changed in this step (decision "dotnet watch and Hot Reload (implementation record; choices for review)").
  - **Profiles under `dotnet watch`:** `dotnet watch -lp Desktop` and `-lp Loopback` both work; on loopback the open page reloads by itself after each restart (step 2), and its loop guard stops that after three reloads into documents that each lost their backend within 5 s, which edits a second or two apart on Linux's quick restarts can reach.
- **Agents:** after external edits, the CLI build or `spar dev` is the loop. Start real processes directly, so their whole tree can be stopped.
