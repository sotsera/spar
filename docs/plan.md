Revised 2026-11-13 (second pass the same day, after the M0 spikes and the design discussions), corrected 2026-11-14 after a review of the spikes, and reviewed against the decision log on 2026-11-15, when M1 was split into four slices (decision "Plan and guidance review; M1 split"). ## Goal

Spar is a C# framework for desktop apps with a web frontend: WebView2 on Windows and WebKitGTK on Linux. The backend is C#, published by default as one NativeAOT executable on .NET 11. C# contracts generate the TypeScript client, so the frontend calls the backend through typed functions.

Spar is built for agents first: **an agent should be able to make a change, verify it, and know which build it is looking at.** People use the same tools.

The first real consumer is a SQL Server tool (monitor instances, compare databases, copy data with saved recipes). It is built as a separate app that uses Spar only through its packages.

## Settled decisions

Details and evidence in `docs/decisions.md`.

| Decision | Reason |
|---|---|
| Two desktop hosts from the start: Windows (WebView2) and Linux (WebKitGTK). The core is host-neutral; each host supplies its channel, transport, origin checks, automation and native services. | User decision. The Linux spike worked on both WebKitGTK APIs, and the SQL tool's data layer matched Windows on Linux. |
| NativeAOT by default. Per app, the author may publish on CoreCLR or accept their own AOT warnings. Spar's own code stays warning-free. Never fall back silently. | User decision. SqlClient is not AOT-clean (49–53 ILC diagnostics) but works with them accepted. |
| .NET 11 (SDK 11.0.100), C# 15. `InvariantGlobalization=true` by default, the NativeAOT default; an app turns it off in its own project file (+260,096 B on the minimal baseline app of `docs/evidence/sqlclient-aot`). SqlClient needs it off, so the SQL Server tool turns it off; Spar itself never does (user, 2026-11-14). | Current release; `closed` hierarchies; measured cost. |
| Plain `dotnet build`, `run`, `test` and `publish`, plus IDE builds, work without Spar tooling. The CLI build is the source of truth after external edits. | Agents and people use tools they know; neither IDE regenerates on external edits. |
| A source generator emits all contract C#: dispatch, catalog and serializers. A pre-compile step emits only the generated client. They share one analysis library, and a `DiagnosticAnalyzer` reports located diagnostics. | D1 and the IDE checks: live diagnostics with squiggles, no build needed first. |
| Wire serialization: generated `Utf8JsonReader`/`Utf8JsonWriter` code, with the fuzzing requirements (R0–R4). | Faster to read, 47% smaller than System.Text.Json metadata; at least as fast to write once tuned. |
| Spar build steps are compiled, thread-safe MSBuild tasks (`Runtime="NET"`). Checked by `docs/evidence/msbuild-task-analyzer` (SDK 11.0.100 = MSBuild 18.12.2): the task project references `Microsoft.Build.TaskAuthoring.Analyzer` 18.13.0 (`PrivateAssets="all"`; it runs, about 35 ms, no build-time difference) with Framework and Utilities.Core 18.12.2 as compile-only references. Tasks take the full thread-safe shape now: `[MSBuildMultiThreadableTask]`, `IMultiThreadableTask`, and a `TaskEnvironment` constructor. Under `-mt` only tasks with the attribute stay in-process (32 projects: 255–262 ms against 474–514 ms with `-m:8`); others move to TaskHost processes. The analyzer misses static mutable state, so that stays a review and test rule; its code fixes are not shipped. Its option and four severity raises (MSBuildTask0001, 0009, 0011 and 0013 to warning) are agreed and in the root `.editorconfig` (user, 2026-11-14). `TaskHostFactory` is used only in Spar's own checkout. Variant builds run in-proc through the `MSBuild` task, with per-variant `obj`/`bin`, `RemoveProperties`, and a cross-process lock. | Measured: 7–30 ms warm steps; in-proc variants 1.6–2.2 s faster than `Exec` per call. |
| One `SparVariant` property selects the build variant: `Production`, `Development` or `Test`. Debug builds `Development`, Release builds `Production`, and a test project builds its referenced app as `Test` (the test-host hook, page automation, the UI-thread stall probe) whatever its configuration; `SparVariant` can still be set explicitly. `Test` replaces `DesktopTest` and the spikes' `ManagedTest`, and `Editor` is dropped (decisions "Test strategy: the app runs inside the test process" and "Polished sample apps: a Markdown notebook; the test variant"). In this plan "Debug" means the `Development` variant and "Release" the `Production` variant. | The earlier mode-flag matrix was the main source of fragility. |
| A call has three outcomes: success, a declared typed error, or **outcome unknown**. Cancellation is reported only when the backend confirms it. No automatic retries; subscriptions resume only when their contract allows it. | A lost reply must never be read as "didn't happen". |
| Results are opaque in TypeScript: `await cmd(req).match({ success, errors, failure? })` or `unwrap()`. `failure` is a function (every failure) or an object by `CallError` kind (only those kinds). Other failures go to the app-wide interceptor `onFailure`, and `match` returns `undefined` for them. `unwrap` throws and never reaches the interceptor. `observe` sees every failure. Neither hook can retry or change a result (2026-11-14). | User decision; checked with `tsc` and both language servers. |
| One DI scope per command, from Microsoft DI (`Microsoft.Extensions.DependencyInjection`; user decision 2026-11-14, +0.3–0.9 MB in AOT). Every request belongs to one document, with sender checks. On navigation or close, stop admitting work, cancel, and drop late replies. | Proven in every spike. |
| The desktop origin is `https://app.localhost` on Windows and `spar://app/` on Linux, the same for every app, and never changes between versions. | User decision. `.local` added about 2 s per load after a network change; `app.localhost` loaded in 54 ms and needs no name resolution. The profile is already per app, so one name for every app mixes no data. |
| Tests run the app's own `Program.cs` inside the test process, with service overrides as ordinary DI code and one of three surfaces in front of the backend: none, a browser over loopback, or the app's real window. A launched executable is used only for the Production binary as a black box and for behaviour across processes (section 5). | User decision (2026-11-15). `docs/evidence/test-host`: 0.2–0.6 ms command-level starts; real windows in the test process on both OSes under CoreCLR and NativeAOT, with nothing leaked. |
| Isolated data and WebView profiles per test run, under `artifacts/`. Wait for the browser to exit before reusing or deleting a profile. | Repeatable tests; the browser sometimes takes about 6.5 s to exit. |

### Definition of done

A feature is done when every item that applies to it is true (user, 2026-11-15; decision "Plan split, additions and the M1a scope"):
- **Decided:** the decision is in `docs/decisions.md` (a user decision where this plan says so), and the plan and its design file agree with it.
- **Shown:** a public API has a compiled example in `docs/app-model.md`, and its check passes.
- **Tested** at the levels of section 5 that can show its failures: at least a unit or command test; a browser test for page-facing behaviour; a window test on both hosts for host behaviour; the NativeAOT lane passes. A feature that exists on one host only says so in the plan.
- **Safe:** its security default follows section 3c, with the C# opt-in and its documentation for anything a default blocks.
- **Documented:** the user-facing page (plain Markdown, compiled examples), the skill that covers the area, and new pitfalls.
- **Checked by a person, where needed:** rows in "Checks that need the user at the PC" for what an agent cannot run.
- **Measured:** the budgets it touches are measured (below), and the evidence file records the environment, commands, numbers and what was not verified.
- **Clean:** no warnings, no suppressions without the user's agreement, and `eng/check-size.cs` passes.

### Risks

The biggest risks, each with what retires it. Update the table when a risk is retired or a new one appears.

| Risk | Why it matters | Retired by |
|---|---|---|

#### M2b: `spar dev`

Spar's own supervisor (decision "M2's decide-first questions", 5): it builds the app's Development variant, starts it, and on request builds again and either restarts the app or returns the compiler diagnostics at file and line; the development server is kept across restarts (the app already reuses the one `obj/spar-dev-server.json` records), every process it starts is in a job object (Windows) or a process group (Linux) from creation, with a closed stdin. Hot Reload stays with `dotnet watch` and the IDEs.

**Decide first** (settled with the user 2026-11-26, every recommendation taken; decision "M2b's decide-first questions"):
1. **How a reload is asked for.** Decided: an explicit `spar reload`, which reaches the running `spar dev` over an owner-only local socket of its own, found through `obj/spar-dev.json` with a token (the devtools' transport and protocol), so an agent reloads when its edits are complete and never gets a build of a half-saved change. Not taken: `spar dev` also watches the project's files and reloads on save (`--watch`); or only file watching.
2. **What happens to the running app while it rebuilds.** Decided: the app keeps running until the new build succeeds. `spar dev` builds the ordinary Development output in `bin/`, starts the app from a copy of it (so on Windows the build never meets a locked file, and the IDE can build meanwhile), and swaps only after a successful build; a failed build leaves the old app running and answers with the diagnostics. Not taken: stop the app, build, start it again, so a failed build leaves nothing running.
3. **How the app is stopped for a restart.** Decided: a devtools request that runs the host's own session end (the path Windows' `WM_ENDSESSION` and Linux's `SIGTERM` take: close guards within their budget, the services disposed, 4 s at most), then the app's process tree is killed if it is still there; an app built with `SparDevtools=false` is killed at once. Not taken: kill at once always; or the OS's session end from outside (`WM_ENDSESSION` to the window, `SIGTERM`), which a loopback app on Windows lacks.
4. **Where the app's window appears.** Decided: on the user's desktop; later restarts take the previous window's place and size and do not take the focus; and `spar dev --private` runs the app where the user cannot see it (a desktop of its own on Windows, as M2a's evidence did; a private Xvfb on Linux), where the devtools still work. Not taken: the desktop only, with restarts not taking the focus; or the desktop with plain restarts.
5. **Which run it starts.** Decided: a launch profile from `Properties/launchSettings.json`, as `dotnet run` and the IDEs read it (`spar dev -lp Loopback`; by default the first profile that runs the project), so the environment and arguments match F5; `spar dev` starts the built executable itself, not through `dotnet run`. Not taken: a `--host window|loopback` option and no profiles.
6. **When `spar reload` answers, and with what.** Decided: after the build and, when it succeeded, once the new run reports `ui-ready` (or exits, or 60 s pass), so the next `spar tree` finds the new page; the answer lists the errors and warnings at file, line and column (C#, Spar's diagnostics and the TypeScript type-check, all from MSBuild's own diagnostics), the build's time, the new run id and the start time, or the app's exit code and last output lines when it failed to start; text or `--json`, with `spar doctor`'s exit codes (0, 1 warnings, 2 errors). Not taken: answer right after the build, without waiting for the page.
7. **`spar dev`'s lifetime.** Decided: one `spar dev` per project (a second one says where the first runs and exits 64); it runs in the foreground, printing the app's output and each reload's result, until Ctrl+C or `spar dev --stop`, which ends everything in its job; when the app exits on its own (its window closed), `spar dev` keeps running and says so, and `spar reload` starts it again. Not taken: `spar dev` ends with the app.

**Build** (all four built 2026-11-26; decision "M2b: spar dev (implementation record; choices for review; 2026-11-26)", `docs/evidence/m2b-spar-dev.md`, user guide `docs/guide/spar-dev.md`):
1. **The host side:** the devtools' `stop`, which runs each host's own session end (Windows' `WM_ENDSESSION` sent to its own window, Linux's `SIGTERM` path, loopback's Ctrl+C path); a Development build's Windows host takes `SPAR_DEV_WINDOW` (the previous window's place and size) for its first window.
2. **Processes:** one job object for the session on Windows (every child joins it at creation, in a process group of its own, with `NUL` as its input), a process group per child on Linux (`setsid`, killed with its parent); `--private` on a desktop of its own (Windows) or a private Xvfb (Linux).
3. **The supervisor:** the build (`dotnet build` with MSBuild's own file loggers for the diagnostics, its nodes and compiler server the session's own), the run's copy under `obj/spar-dev/`, launch profiles, the start and its `ui-ready`, the stop, the socket and `obj/spar-dev.json`; `spar dev`, `spar dev --stop` and `spar reload` with text and `--json`.
4. **Tests and evidence:** the tool's unit tests, the devtools' `stop`, the production boundary's marker, the smoke runs on both hosts, `docs/evidence/m2b-spar-dev.md`, the user guide.

**Exit:** `spar reload` answers on Windows and Linux with a failed build's diagnostics at file and line while the previous run keeps running, and with the new run at `ui-ready` after a good one; the restart goes through the session end; nothing `spar dev` started outlives it; a Production executable carries none of it (the production boundary test); the evidence and the user guide are written.

#### M2c: `spar snap` and scenes

A one-shot capture (section 6, `docs/design/agents.md`): `spar snap` runs a named scene of the app, writes a PNG of its page, its accessibility tree and the bridge calls it made, then exits; no session, no port. Scenes are C# in the app's test project, run through the test host with its safety defaults and a fixed clock, so the app's own builds carry no scene code (decision "M2's decide-first questions", item 6). Determinism (risk F in `docs/design/testing.md`: clock, fonts, scale) is what makes a capture worth comparing.

**Decide first** (settled with the user 2026-11-26, every recommendation taken; decision "M2c's decide-first questions"):
1. **How a scene is written.** Decided: a static method in the end-to-end test project marked `[SparScene("new-page-dialog")]`, taking a `SparScene` whose `StartAsync<Program>(o => …)` starts the app on the Window surface with the scene's defaults (the fixed clock, light theme, a fixed window size) and the test's own options (service overrides, data), then drives the page with `app.Page` as a window test does; the capture is taken when the method returns, and the scene disposes the app. Spar's generator lists the scenes (no reflection, so the NativeAOT lane works), and every scene also runs as a window test, so a broken scene fails `dotnet test`. Not taken: an ordinary xUnit test that calls `app.SnapAsync("name")`, run by `spar snap` through `dotnet test --filter`; or a scene class with separate setup and steps methods.
2. **How `spar snap` runs one.** Decided: it builds the end-to-end project (Debug, so the app as its Test variant) and runs the built test executable with `--spar-scene <name> --spar-snap-out <folder>`, which Spar's generated code answers before the test framework starts (run the scene, write the files, exit with its own codes), so a capture costs one app start and no test platform. Not taken: through `dotnet test --filter-trait SparScene=<name>`, the files written by the test; or a separate scene runner project.
3. **Steps beyond the scene's own.** Decided: none: the steps are the scene's C#, and exploring the page by hand is `spar dev` with the devtools (`spar click`, `spar screenshot`). Not taken: `spar snap <scene> --steps <file>`, a list of devtools actions (`click`, `fill`, `wait` with the same targets) run after the scene, so an agent can capture a variation without writing C#.
4. **The fixed clock.** Decided: one instant per scene (`2026-01-15T09:30:00Z` unless the scene sets `scene.Time`), given to the backend as the test host's `TimeProvider` and to the page through the host-injected script (`Date`, `Date.now`), both advancing in real time from that instant, so timers and timeouts work and "edited 5 minutes ago" reads the same every run; timers are not frozen or fast-forwarded. Not taken: a frozen clock that the scene advances by hand; or the backend only.
5. **What keeps the image the same.** Decided: on the same machine and OS a scene gives the same PNG every run: the page at a fixed size (1280 × 800 CSS pixels) and a device scale of 1, light theme, `prefers-reduced-motion: reduce`, the caret hidden, and the capture taken once the page has been idle (no bridge call running, no animation, fonts loaded) for 200 ms; checked by a test that snaps twice and compares the bytes. Across machines and between Windows and Linux nothing is promised (fonts and rendering differ). Not taken: also bundle fixed fonts for scenes; or no idle wait.
6. **What it writes, and where.** Decided: `obj/spar-snap/<scene>/` in the end-to-end project (or `--out <folder>`): `page.png`, `tree.txt` (the devtools' tree format) and `tree.json`, `calls.json` (every bridge call with its timing and outcome), `problems.txt` (`app.Problems`, the page's errors and console messages); the command prints the folder and a one-line summary per scene. No comparison with a stored image in M2c. Not taken: write next to the test project as committed baselines and compare (`--check`); or print the files' contents.
7. **The command line.** Decided: `spar snap --list`, `spar snap <scene>...`, `spar snap --all`, with `--project` (the app or its end-to-end project; from the app, the end-to-end project is the one beside it whose `SparTestedApplication` names it and that has scenes), `--out` and `--json`; exit codes 0 written, 2 a scene failed (its exception and the last lines of its log), 64 a wrong command line. Not taken: grouped as `spar scene list` and `spar scene snap`.

**Build** (all four built 2026-11-26; decision "M2c: spar snap and scenes (implementation record; choices for review; 2026-11-26)", `docs/evidence/m2c-spar-snap.md`, user guide `docs/guide/spar-snap.md`, `docs/app-model.md` 6.15):
1. **The scene API** in Spar.Testing: `[SparScene]`, `SparScene` with its clock (the backend's `TimeProvider` and a script of the page's world), the fixed viewport at scale 1, reduced motion and software rendering for its window, the call recorder from the app's first call, and the capture (still, idle, PNG, tree, calls, problems).
2. **The generator:** the scenes' registration in a module initializer, the `--spar-scene-list` answer, one window test per scene, and SPAR110 to SPAR112.
3. **`spar snap`:** the end-to-end project found from the app or its own folder, its Debug build (or `--no-build`), the list, one capture per scene through the test executable's xUnit runner, `tree.txt`, the summary and `--json`.
4. **Tests and evidence:** the generator's and the tool's tests, `Spar.WindowTests`' scene tests (two captures the same bytes, both clocks), the Notebook's scenes, the smoke runs on both hosts.

#### M2d: the optional OpenTelemetry layer, client telemetry and Aspire

Section 6b (`docs/design/agents.md`): an opt-in layer that exports the backend's traces, metrics and logs over OTLP only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, a page module that sends the page's spans through the backend (each host serves `/_spar/otlp/*` on the page's own origin, 404 without the layer, and the layer forwards the bytes unchanged), `traceparent` from each page call to its backend span, and the Aspire dashboard as the development viewer. Settled since M0 (decisions "Optional OpenTelemetry layer", "Browser telemetry through the host: confirmed", "Browser telemetry: how the page starts it" and "M2's decide-first questions", item 7): the OpenTelemetry SDK and OTLP exporter in the layer; the relay's 503 for 5 s after a failure and no replay; the settings in the host-injected script on desktop hosts and `POST /_spar/otlp/config` beside the mount on loopback; the page chunk loaded lazily, only with the layer; no click spans and no `zone.js`, `traced(name, fn)` to group an interaction's calls; a bounded flush before a window closes; `OTEL_SERVICE_NAME`, with `-page` for the page; an Aspire recipe first, a hosting package only if it needs more than a few lines.

**Decide first** (settled with the user 2026-11-26, every recommendation taken; decision "M2d's decide-first questions"):
1. **How an app turns the layer on.** Decided: a package reference to `Spar.OpenTelemetry` and one call in `Program.cs`, `spar.Telemetry(otel => …)`, whose lambda takes the OpenTelemetry builder so the app adds its own instrumentation (HttpClient, SqlClient) and resource attributes; the build sees the reference and gives the page its module, so the page needs no code; nothing is exported until `OTEL_EXPORTER_OTLP_ENDPOINT` is set at run time. Not taken: the package reference alone, with fixed defaults and no code; or an MSBuild property (`<SparOpenTelemetry>true</SparOpenTelemetry>`) that adds the package.
2. **What the backend exports.** Decided: traces (Spar's `Spar` activity source, each bridge call's span, and what the app adds), metrics (Spar's `Spar` meter, `spar.call.duration`, and what the app adds) and logs (the app's and Spar's `ILogger` lines through Spar's logger factory, at the levels the app's log file has), with OpenTelemetry's standard variables honoured (`OTEL_TRACES_SAMPLER`, `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_RESOURCE_ATTRIBUTES`). Not taken: traces only, metrics and logs as the app's own additions.
3. **What the page sends.** Decided: traces only: one span per bridge call (the parent of its backend span), the spans of `traced(name, fn)`, and the document's load; the page's errors and console messages already reach the backend's log (and so its OTLP logs) through the host, so the page exports no logs of its own. **Subscription resumption** (user decision):

| Level | Who | Setting | Default |
|---|---|---|---|
| Contract | Backend author, in C# | `[SparSubscription(Resume = SubscriptionResume.Automatic \| Manual)]` | `Automatic`: a subscription must not have side effects. Anything that does, such as draining a queue or creating server-side sessions, is marked `Manual`. |
| Call | Page, in TypeScript | `{ resume: "automatic" \| "manual" }` | The contract's value. The page may only be more cautious: `Manual` subscriptions are typed as `resume?: "manual"`. |
| App | SDK configuration | `configureSpar({ resume: "manual" })` | Lowers the default; it never raises it above a contract's value. |

- **Automatic resume:** re-subscribe with backoff (for example 250 ms doubling to 5 s) when the bridge is back. Emit `reconnecting`, then `reset` before the first new event, then `resumed`. Give up after a limit (for example 30 s) with an outcome-unknown `CallError` (`lost`).
- **One-shot streams are never resumed, and unary commands are never retried.**
- **A resume cursor** is a later, author-opt-in extension.

#### M3a: streams and subscriptions

Section 2c (`docs/design/bridge.md`) and the table above: `IAsyncEnumerable<T>` and `IAsyncEnumerable<Result<T, TError>>` commands as one-shot streams and `[SparSubscription]` ones as subscriptions, on both hosts and loopback, through the generated dispatch, serializers, TypeScript client and typed C# test clients; credits on every host, in-band failures, the `events` slot, coalescing, resumption at three levels, trace context. Already in place since M1a: the message types (`stream`, `credits`, `items`, `end`, `event`, `failure`, `cancel`) in the codec and the SDK's protocol, with nothing dispatching, generating or serving them. Settled since M0: the drop-oldest subscription buffer with `gap` events, the required `events.reset`, a coalesced subscription's capacity of 1, a pull stream stopping at its next `yield`, `cancelled` only on the backend's confirmation, and no replay.

**Decide first** (settled 2026-11-27: the user accepted every recommendation; decision "M3a's decide-first questions"):
1. **The coalesced subscription's name** (left "to settle in M3"). Recommended: `[SparSubscription(LatestOnly = true)]`, which says what the page gets. Not taken: `Coalesce = true`; `Mode = SubscriptionMode.Latest`.
2. **Flow control's numbers.** Recommended: a stream starts with 256 items of credit, which the page tops up once half is used; items travel in batches of at most 64 items or 64 KB, or what a 16 ms window collected; a subscription's buffer holds 256 items by default (`Capacity`), dropping the oldest with a `gap` that counts them. Each number is measured at the slice's exit against the plan's round-trip budgets. Not taken: one item per message; unbounded subscription buffers.
3. **When a subscription resumes.** Recommended: when the same document's channel comes back (loopback's reconnect, and the backend's restart under `dotnet watch` or `spar reload` while the page stays), with the table's backoff (250 ms doubling to 5 s) and its 30 s limit, ending `transport` / `lost`; a new document (a reload, a renderer's recovery) starts with no subscriptions, as every call does. Not taken: resuming across documents.
4. **The typed C# test clients** (plan section 5). Recommended: a stream is `IAsyncEnumerable<Result<T, TError>>` (or of `T`), a subscription an `IAsyncEnumerable` of an item that is a value, a declared error or an event (`Reset`, `Gap(count)`, `Reconnecting`, `Resumed`), and the test host can drop and restore the channel to test resumption. Not taken: subscriptions without events in tests.
5. **Tracing** (section 6b). Recommended: one span per stream or subscription, from its start to its end, with its item count, drops and resumes as attributes, the page's span its parent as for a call, and no span per item. Not taken: a span per batch.
6. **The exit's proof.** Recommended: the contracts of `docs/app-model.md` with streams and subscriptions (`copyJobs`, `status`) leave `tests/AppModel/Real`'s exclusions and build through real Spar; the Notebook gains one live feature (pages changed by another window, as a subscription) with its window test; budgets: 20,000 subscription events a second delivered whole, and 100,000 stream rows within the browser test's budget. Not taken: proof through Spar's own tests only.

**Built** (2026-11-27, on `m3`; decision "M3a: streams and subscriptions (implementation record; choices for review; 2026-11-27)", `docs/evidence/m3a-streams.md`): `IAsyncEnumerable` commands as streams and `[SparSubscription(Capacity, Resume, LatestOnly)]` ones as subscriptions (SPAR017, SPAR018), through the generated dispatch, the bridge (credits in items, batches, the drop-oldest buffer, `StreamsOpen`), the generated TypeScript and the SDK's iterator, typed C# test clients with `DropChannel` and `RestoreChannel`, page-test fakes (`spar.stream`), resumption on a new loopback channel for the same page, one span per stream or subscription; `copyJobs` and `status` built through real Spar; the Notebook's live changes with window and browser journeys; on Windows and Linux.
