# Work on the Linux WebKitGTK host

Use `spar-native-interop` for declarations, GObject ownership and callbacks, and `spar-webview2-hosting` for the Windows side of a cross-host change. Plan section 3 ("Linux", in `docs/design/hosts.md`) holds the design, with page security in `docs/design/security.md` and testing in `docs/design/testing.md`; `docs/pitfalls.md` ("Linux host", "Bridge and loopback", "Page security") holds the evidence.

## API and threads

- **`webkitgtk-6.0` and GTK4 only.** No GTK3 or 4.1 code path and no compile-time switch (decision "Linux host uses WebKitGTK 6.0"). The 4.1 notes in the plan and pitfalls are evidence only. The APIs used need WebKitGTK 2.40, and `JSC_useWasm` 2.48, so the startup check's minimum is 2.48 until M4 sets the supported one.
- **Never block the GLib main loop.** GTK and WebKit run on one dedicated thread with a `GMainLoop`; a `SynchronizationContext` posts to it through `g_idle_add_full`. Backend commands, I/O, synchronous waits, a nested `g_main_loop_run`, large payload parsing and long CPU work never run on it. The scheme handler and `decide-policy` answer from data at hand; anything slower finishes off the thread and completes back on it (plan 3, "The UI thread is never blocked"). Resource-usage sampling also runs off the loop.
- **Bindings:** `[LibraryImport]` and `[UnmanagedCallersOnly]` against glib, gio, gtk and webkit. The NativeAOT exe links only glibc and loads the libraries at first use, so a missing one must be caught by the startup check, not by a `DllNotFoundException`.

## Startup

- **Set with libc `setenv` before GTK, WebKit or any other thread starts** (never `Environment.SetEnvironmentVariable`, which native `getenv` and child processes do not see):
  - `JSC_useWasm=false`, so `WebAssembly` is absent in the page, workers and frames; the C# opt-in sets `true` and adds `'wasm-unsafe-eval'` (decision "WebAssembly off on Linux"). As built (M1c step 5, `EngineEnvironment`; decision "Linux WebAssembly off by default"): `LinuxApp` resolves the page security (`PageSecuritySetup.Resolve`, the build's copy from the catalog, so no app code runs twice) after the prerequisite checks and hands it to the window; `JSC_useWasm` is written with `overwrite` 1 before the GPU check, so an inherited value never decides it, `AllowBrowserEnvironmentOverrides()` or not, and logged (`WebAssembly off: JSC_useWasm=false`, with the inherited value it replaced). The other inherited `JSC_*` options are the environment filter's (below, "Environment overrides"). The page security is the build's, so a test app's second configuration is a second build (the bridge probe's `-p:BridgeProbeWebAssembly=true`);
  - `GSK_RENDERER=cairo` for the startup error dialog always, and for the app itself only on a software GPU. Never change it when the user already set it (decisions "Software GPU default" and "Guidance review applied", point 3). As built (M1c step 2), no prerequisite check starts GTK, so this is set only once the outcome is known: for the message when there is a problem, for the app on a software GPU. `setenv` with `overwrite` 0, and the variables reach every child process.
- **Software GPU default** (`GpuCheck`; decision "M1c: the software-GPU detection method"): before GTK, the render nodes first (none openable, or only `vgem`/`vkms` by `drmGetVersion`, means software, 0.1 ms), else a surfaceless EGL display and a GLES context reading `GL_RENDERER` (llvmpipe, softpipe, lavapipe, SwiftShader, swrast; any failure counts as software; use `EGL_KHR_no_config_context`, Mesa's surfaceless display may offer no configuration). On software, `WEBKIT_DISABLE_DMABUF_RENDERER=1` (which also sets WebKit's acceleration policy to never) and `GSK_RENDERER=cairo`. The option is `spar.Browser(b => b.HardwareAcceleration(Auto | Always | Never))`, Linux only, logged at start-up with what was found and its cost; the user's own variables always win.
- **Prerequisite checks, in plan 3's order** (`Prerequisites`; built in M1c step 2 with single instance after the display and every library check before `gtk_init_check`, so the environment is still settable): display variables (exit 6 with no display, before anything can start D-Bus), GLib, then GTK 4, `g_set_prgname` (otherwise the window is "Unnamed Window"), `gtk_init_check`, WebKitGTK and its version, the helper folder (found through `/proc/self/maps`), `bwrap` and `xdg-dbus-proxy`, then a trial `bwrap` run, which catches a denied sandbox in 1.5 ms instead of an abort after 4–7 s. Exit codes are fixed for every app and the same on both OSes: 3 missing, 4 too old, 5 broken, 6 no graphical session, 7 OS too old (plan 3, "Missing prerequisites").
- **The message** (`StartupFailure`): `GtkAlertDialog` once GTK 4 is initialised (as built, on a main loop of its own when no window exists yet); otherwise kdialog, zenity, yad, a D-Bus notification, notify-send, then xmessage (built: kdialog, first on KDE, zenity and xmessage; a program that exits 126 or 127 is skipped). As built, stderr and `app.log` are written; the journal is not yet. Name the package to install (`libwebkitgtk-6.0-4` on Ubuntu). Write stderr when present and the journal (native protocol or `/dev/log`). The app's C# hook may replace the dialog, never the exit code.
- **Window order:** create the view with its network session, attach it, call `load_uri`, then present the window at once in the theme colour. Shown first, the page loses focus and the first Tab. A view that is never presented is a hidden page with throttled timers. Maximize only after the first map, and unrealize after hiding (WSLg Wayland pitfalls).
- **Theme (plan 3d):** a GTK CSS provider for the window, `gtk-application-prefer-dark-theme`, and an opaque `webkit_web_view_set_background_color` (transparent shows black). Read the XDG Settings portal's `color-scheme` and its change signal, falling back to GTK settings; never read back a setting the host wrote. Set no theme name. As built (`WindowTheme`): the saved `color-scheme` choice first; the portal read on the main thread before GTK with `NO_AUTO_START` and a short limit (a portal that is not running is never started); and the X window's background pixel set to the theme's colour after `gtk_widget_realize`, or a non-composited X11 window shows what was beneath it until GTK's first paint.

## Serving, bridge and page security

- **The origin is `spar://app`,** because WebKitGTK cannot intercept `https` (decision "Desktop origin"). It is a secure context, but it stores no cookies, and Cache Storage rejects it. No service worker registers from it: `register()` rejects with a `TypeError` that asks for HTTP or HTTPS (2.52.6; M1c step 5's test pins it); dedicated and shared workers run. The origin keys stored data, so it never changes without a migration.
- **Scheme responses:** answer every request, serve stored entries in place with `g_bytes_new_static`, and decode Brotli entries at start on a background thread (WebKit never decodes `Content-Encoding`). Never answer with a redirect: WebKit shows the 302 body as the page. Responses stream with no back-pressure, so never hand over an unbounded producer.
- **Headers on every response, worker scripts included:** the generated CSP, `nosniff`, `Cache-Control: no-store` and the rest of plan 3b. Repeat `Content-Type` inside the header set passed to `webkit_uri_scheme_response_set_http_headers`, or WebKit blocks the app's own CSS, scripts and workers. `connect-src` names `spar://app` (checked by `spikes/linux-gpu-csp`: `'self'` would let `wss://app` through).
- **Built in M1c step 1** (`src/Spar.Linux`): what the origin answers is the core's `PageResponder`, shared with Windows; `SchemeServer` turns it into a `WebKitURISchemeResponse`, in place (`g_bytes_new_static`) for files stored in the executable's image (`SparFrontend.IsImageMemory`), as a copy otherwise, and holds a request (a reference on it) that arrives before the page is prepared. The scheme is registered secure and CORS-enabled on the view's context, WebKit's default one, so once per process.
- **No origin information:** scheme requests carry no `Origin`, and script messages do not say which frame sent them. Keep the navigation lock in `decide-policy` (never configurable), inject the bridge into the top frame only, and run it in an isolated script world with a relay in the top document only (plan 3, "Origin policy"; built and tested against foreign iframes in M1c). Same-origin iframes stay blocked by the CSP unless the app opts in, because their messages look like the window's.
- **Page security as built (M1c step 4;** decision "Linux page security (implementation record; choices for review)"): `PageGuard` on the view's signals, answered on the loop from memory and failing closed (a decision that throws is ignored, a permission denied).
  - **`decide-policy` has no main-frame flag,** and the view still names the old address at `LOAD_STARTED`: navigations go ahead only to the app's origin and to addresses the app declared in `csp.FrameSrc(…)` (`NavigationRules.IsDeclaredFrame`); everything else is ignored and logged (100 lines a run), `about:blank` and `about:srcdoc` included, since either commits in the window (a frame keeps its first, blank document; `srcdoc` frames stay empty). A load that starts right after a declared frame address was let through is taken for the window's own: stopped at its start, and its main-frame response ignored as a backstop; the document and its bridge stay. A foreign document that commits anyway brings the app's page back. New-window decisions are always ignored; an allowed address (`NavigationRules.ExternalRefusal`, shared with Windows) opens with `g_app_info_launch_default_for_uri` on a thread of its own, only with WebKit's gesture flag and a real button, key or touch event on the view within 5 s (a capture-phase `GtkEventControllerLegacy`): WebKit's flag alone is set for script right after a host-started load.
  - **`permission-request`:** decided by the request's GType name (`PageGuard.Decide`): geolocation, camera and microphone (each needed), clipboard and the device list (with the camera or the microphone) by the declarations; notifications, screen capture, pointer lock, media keys, storage access, XR and unknown kinds always denied; only from the app's page; logged once per kind. `query-permission-state` answers "denied" or "prompt"; WebKit adjusts what the page sees (pitfalls).
  - **Reports:** the relay runs the violation listener in its own world with Windows' limits (`CspViolationLog.Listener*`), its batches read on the bridge's reader without a session; `report-uri` is answered 204 at once and, within `ReportLimiter`, its body read with `g_input_stream_read_all_async` into a native buffer of 16 KiB + 1, never on the loop. Workers' violations reach neither channel on WebKitGTK.
  - **Teardown:** web processes still there 3 s after the window is gone are ended (SIGKILL), never the network process, which is waited for again: a window load that never committed left one that made the app abort about 10 s after its exit.
- **The bridge:** the script message handler (6.0 passes a `JSCValue*` and registers with a world name) from page to host, `evaluate_javascript` or `call_async_javascript_function` from host to page. Injected user scripts obey the page's `eval` ban, unlike on WebView2, so they must not use `eval` or string-built functions.
- **The relay as built** (`BridgeRelay.js`, `ScriptBridge`; decision "The Linux host, first slice"): the handler `spar` exists in the isolated world `spar` only; the relay is a user script of that world, top frame, document start, allow-list `spar://app/*`, and checks `location` again. Worlds share only the window's events, so the page's SDK (`webKitChannel()`, picked by `hostChannel()` when `location.protocol` is `spar:`) dispatches `spar:send` with a string `detail`, and the host's `evaluate_javascript` in world `spar` calls `sparRelay.deliver([...])`, which dispatches `spar:receive`. Host messages are encoded as JavaScript string literals off the loop (U+2028, U+2029 and lone surrogates escaped) and flushed once per loop turn. Documents close at `WEBKIT_LOAD_STARTED` and open at `WEBKIT_LOAD_COMMITTED` on the app's origin only; a session is created by the reader for its document's first message, once the services exist.
- **Debug proxy** (decision "Debug serves Vite through the app's own origin"): Development-variant code only. The scheme handler fetches from Vite with `HttpClient` off the loop and answers with a `WebKitURISchemeResponse`, with the same header rules as Windows. The Linux path is an M1 check.

## Production defaults (plan 3c)

- No `enable-developer-extras`, no windows opened by JavaScript, no `file://` access, downloads denied, `javascript-can-access-clipboard` off (it bypasses the clipboard permission check). As built (M1c step 6, `BrowserDefaults`; decision "Linux security defaults (implementation record; choices for review)"), with Windows' opt-ins and log lines:
  - the view's settings in `BrowserView.Create`, before the first load: developer extras only in Development or with `AllowDevTools()`; clipboard, script windows, both `file://` accesses and top-level `data:` off, set explicitly though they are WebKit's defaults; one line "Browser settings set (…)" (Development: "read back", from the getters, which Production does not carry);
  - `download-started` on the network session cancels with `webkit_download_cancel` unless `AllowDownloads()`; `run-file-chooser` answers with `webkit_file_chooser_request_cancel` unless `AllowPagePicker()`; `context-menu` (6.0: view, menu, hit test, data) removes every item but Cut, Copy, Paste and Select all (editable) and Inspect Element (devtools) by stock action unless `AllowContextMenu()`, and shows none when empty or in the automated mode; a signal that WebKit does not have stops the start, never a missing default;
  - `PageGuard` ignores `WEBKIT_NAVIGATION_TYPE_BACK_FORWARD` unless `AllowHistoryNavigation()`, but **the host's own reload after a lost or ended web process arrives as a back-forward navigation too:** call `PageGuard.HostReloads()` before every `webkit_web_view_reload`;
  - WebKitGTK binds no browser key (reload, print, find, zoom, history; its inspector only through Inspect Element), the mouse's back button does nothing, and there is no password manager: `AllowAcceleratorKeys()` and `AllowPasswordSaving()` change nothing here, and Development has no reload keys (M1d);
  - **GTK 4 opens its own inspector on Ctrl+Shift+I and Ctrl+Shift+D in every app** (`org.gtk.gtk4.Settings.Debug` defaults to on), which can change any object of the process: `BrowserDefaults.KeepGtkInspectorClosed` adds a key controller in the window's bubble phase that stops those two keys outside Development, after the page has had them. Never change the user's GSettings for it. `GTK_DEBUG=interactive` opens it at start: Production removes `GTK_DEBUG` with the `JSC_*` options (`EngineEnvironment.Decide`).
- **Permissions:** WebKitGTK ignores `Permissions-Policy`, CORP and COEP, so the `permission-request` handler is the only gate. Deny anything the app did not declare.
- **Environment overrides:** ignore exactly `WEBKIT_INSPECTOR_SERVER`, `WEBKIT_INSPECTOR_HTTP_SERVER` and `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS` unless the app calls `AllowBrowserEnvironmentOverrides()`, in every build; in a Production build also every inherited `JSC_*` option (user decision 2026-11-20; Development keeps them; `JSC_useWasm` is always the declaration's). Let every other variable through, in particular the GPU workarounds (`__NV_DISABLE_EXPLICIT_SYNC`, `WEBKIT_DISABLE_DMABUF_RENDERER`, `WEBKIT_DISABLE_COMPOSITING_MODE`). As built (`EngineEnvironment.Filter`, M1c step 6): after single instance and before any WebKit library is loaded, the names are read from libc's `environ` (never .NET's copy, which misses `setenv` and `unsetenv`), removed with `unsetenv` and checked with `getenv`, removed from .NET's copy too (`Environment.SetEnvironmentVariable(name, null)`), and each is named in a warning, never its value; one that stays stops the start with exit 70. In-process removal is enough on the NativeAOT executable: no inspector port, the web process under `bwrap`, no override or `JSC_*` in the web or network process's `/proc/<pid>/environ` (read the children's: the app's own `/proc/self/environ` keeps the strings it started with). With both inspector variables set, WebKitGTK 2.52 opened only the HTTP one. A release build refuses `JSC_useDollarVM` ("invalid option", restricted), so no `$vm` reaches the page.
- **The web-process sandbox is always on.** It needs a non-root user and user namespaces; never work around a denied sandbox by disabling it.

## Lifetime

- **Single instance before the network session exists:** a lock file plus a Unix socket, which forwards the arguments in 4–10 ms and fails clearly after 2 s on a hung first instance. Not GApplication uniqueness. A second instance on the same folders silently loses `localStorage`. As built (`SingleInstance`, M1c step 2): `instance.lock` in the data root under an exclusive `flock`; the socket `spar-<dev>-<ino>.sock` in `XDG_RUNTIME_DIR` (else the abstract namespace), both ends checking `SO_PEERCRED`; Windows' frame plus the launcher's activation token for `gtk_window_set_startup_id`; hand-over 1.6–1.9 ms, exit 8 at 2.06–2.09 s. No .NET hash for the name: on Linux it needs OpenSSL.
- **Data folders:** pass the app's XDG data and cache folders to `webkit_network_session_new` explicitly; tests use ephemeral sessions. Clear data with `webkit_website_data_manager_clear` (`ALL` is `0xFFF` on 6.0). As built (M1c step 4): `SparFolders.Profile`, named `WebKit` on Linux (`WebView2` on Windows; decision "The browser profile folder per OS") unless `spar.Folders(f => f.Profile(…))` moves it, which must be absolute (exit 70 otherwise), and `cache/WebKit` under the data root; the folders the session reports back (`webkit_website_data_manager_get_base_*_directory`) are recorded in `BrowserProfile` and a difference is logged. Nothing of WebKit's is written elsewhere under the run's `HOME`; Mesa writes `~/.cache/mesa_shader_cache`.
- **Shutdown:** no data waits on the browser (320 runs lost nothing; decision "Profiles and shutdown"), but keep the main loop running until the web processes exit (3–24 ms; 17–49 ms in step 1, but 510–545 ms with acceleration on llvmpipe); terminate a hung web process first, or it outlives the app by about 10 s. WebKit gives no pids: the host waits for its descendants named `WebKit*` (`/proc/<pid>/task/*/children`, polled off the loop, 3 s at most). Destroying the window runs `pagehide`, `visibilitychange` and `unload`, not `beforeunload`, so required cleanup never depends on the page.
- **Recovery:** handle `web-process-terminated`. As built, as on Windows: one silent reload, given back at the next `ui-ready`; a second loss before it ends the app with exit 5 and a `GtkAlertDialog`; `TERMINATED_BY_API` (the host's own) is not recovered.
- **Heartbeat** (plan 3, "Hung pages"): as on Windows, armed at document creation and skipped for hidden or minimised windows. `is-web-process-responsive` stays true for an idle hang, so rely on the heartbeat. "Reload page" means `webkit_web_view_terminate_web_process`, then one reload. As built (M1c step 3; decision "Linux hangs: heartbeat, reload and shutdown prompt"):
  - the rules, dialogs, close-request side and shutdown watch are the core's, shared with Windows (`src/Spar/Hangs/`: `PageWatch`, `ShutdownWatch`, the `IPageWatchHost` seam); `LinuxPageHost` is the Linux side. Change behaviour there, not per host;
  - the relay answers `ping` itself, in the `spar` world (the page never sees it), and the host reads the short `pong` on the loop before the reader, so a document is armed at `LOAD_COMMITTED` and a page that never connects is still pinged; the close request (`close-request`) needs the document's session, which exists once the page has sent its first message;
  - the reload is issued when `web-process-terminated` reports `TERMINATED_BY_API` for the host's own termination, never directly after the call; a hung page's process is also ended before its window is destroyed;
  - the prompts are `GtkAlertDialog`s with a `GCancellable`, cancelled on the loop only (GTK destroys the dialog from the cancellable's signal), first button default and cancel; the main loop keeps running until the services are disposed, so the shutdown prompt can show (unowned) on it; "Exit now" sends SIGKILL to the app's remaining `WebKit*` descendants, then `_exit(10)`;
  - Development builds answer prompts from `SPAR_DEV_PROMPT_ANSWERS` (`first`, `second`, `none`, each `@<ms>`) after showing them, besides Windows' triggers (`SPAR_DEV_HEARTBEAT_MS`, `SPAR_DEV_PAGE_HANG`, `SPAR_DEV_UI_STALL_MS`, `SPAR_DEV_SLOW_DISPOSE_MS`). Tests never answer with input.

## Native services

- **Title bar drawn by the page:** WebKitGTK ignores `app-region`, so the injected script asks the host to move or resize. Start `gdk_toplevel_begin_move` after a 4 px threshold (on press, GTK4 loses the double-click), then call `gtk_event_controller_reset` on every controller of the view, or the web processes outlive the window. Keep an empty, hidden title-bar widget so the CSD shadow and edges stay. No window manager tested offered the window menu.
- **Placement:** size and maximized state everywhere; position only on X11, through `XMoveWindow`; none on Wayland.
- **Tray:** StatusNotifierItem plus dbusmenu written on GDBus, implementing the grouped calls (`EventGroup`, `AboutToShowGroup`). With no watcher, report unavailable; `CloseToTray` then minimises.
- **Others:** file and folder dialogs through GTK4, which always uses the portal; print to PDF without a dialog; JavaScript dialogs through `script-dialog`, answered later, never with a nested loop; power and session events and `KeepAwake` through logind; credentials through libsecret's non-variadic functions (needs a session bus and a Secret Service); process memory from the app's `/proc` tree (`statm` resident − shared; WebKit gives no pids). Capture protection is unavailable on Linux (`isAvailable` false). The decided APIs are in plan 3 ("Native services") and `docs/app-model.md`.

## Running and testing

- **Isolate every run** (plan 5, "Linux isolation"): private `HOME`, every `XDG_*` folder, `XDG_RUNTIME_DIR` and a D-Bus session, all under `artifacts/linux-homes/<run>/` (`AGENTS.md`), with `JSC_*` and inspector variables cleared. GTK, its dialogs, printing, GStreamer, Mesa and the sandbox otherwise write to the real home and `~/.cache`. Never touch the user's WSL home.
- **Trusted input is XTEST:** force `GDK_BACKEND=x11`; in CI, Xvfb in a container run as the app's user (non-root uid 1000, `--init`, the bwrap settings, an optional window manager such as openbox). Disable the DMA-BUF renderer for captures under Xvfb. WSLg cannot test window moves with synthetic input, and its windows appear on the user's desktop. Wayland input stays a check that needs the user.
- **WSL and Docker:** the distribution stops between `wsl` calls (the first window takes about 3.5 s longer), Windows variables need `WSLENV`, Git Bash needs `MSYS_NO_PATHCONV=1` for `/mnt` paths, and NativeAOT needs `clang` and `zlib1g-dev`. Count processes with `pgrep -x`, and stop only processes and containers this session started.
- **The CI Linux lane in WSL:** `eng/wsl/setup.sh` and `eng/wsl/step.sh` run it on a fresh clone of HEAD in `/var/tmp/spar-linux/` (WSL empties `/tmp` on restart), with the run's homes under the clone's own `artifacts/linux-homes/<run>/`: on a Windows drive, `XDG_RUNTIME_DIR` cannot be 0700. Commit first; the clone has only HEAD.
- **The host tests until step 7's Window surface:** `Spar.Tests`' `LinuxHostTests` start `tests/apps/BridgeProbe` (or the Notebook) as a process under the runner's X server, read its log, close it with a `WM_DELETE_WINDOW` client message (`X11Close`) and end web processes with SIGKILL. They skip without `SPAR_LINUX_HOST_APP` and `SPAR_LINUX_TEST_DISPLAY` (and `SPAR_LINUX_NOTEBOOK` for the numbers), so nothing opens on WSLg. `docs/evidence/m1c-host/wsl.sh` runs them in WSL on a copy of the working tree, with an Xvfb unpacked without root.
- **Verify on the real app.** Run the published NativeAOT host for startup, the affected services and shutdown, and check that no web process is left. Time from the host: the page's `performance.now()` has 1 ms granularity. Record the desktop, backend and GPU each result came from; GNOME, KDE, a real GPU, HiDPI and IME go to the plan's table "Checks that need the user at the PC".
