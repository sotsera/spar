# Work on the Windows WebView2 host

Use `spar-native-interop` for declarations and ABI checks, `spar-page-security` for the policy, the navigation lock, permissions and violation reports, and `spar-webkitgtk-hosting` for the Linux side of a cross-host change. Plan section 3 ("Windows", in `docs/design/hosts.md`) holds the design, with page security in `docs/design/security.md` and testing in `docs/design/testing.md`; `docs/pitfalls.md` ("Windows host", "Bridge and loopback", "Page security") holds the evidence.

## Threads and lifetime

- **Never block the UI thread.** The STA only drives the window and the WebView and marshals bridge messages. Backend commands, I/O, synchronous waits (`.Result`, `.Wait()`, `GetAwaiter().GetResult()`, `Thread.Sleep`, blocking locks), large payload parsing and long CPU work never run on it. Callbacks that run on it (`WM_NCHITTEST`, `IStream::Read`, `NavigationStarting`, `WebResourceRequested`, `ScriptDialogOpening`) answer from data already at hand, or take a deferral and finish elsewhere (plan 3, "The UI thread is never blocked").
- **How the app reaches the host:** the generator intercepts `app.Run()` and passes `SparWindowsHost` behind an OS check (decision "The Windows host, first slice"); never find a host by reflection or keep it in static state.
- **Own the STA.** `Main` carries `[STAThread]`; without it environment creation fails with `0x80010106`, which looks like a broken runtime. One STA owns the window, environment, controller and their cleanup, and keeps pumping while native completions are outstanding. Track partial startup, borrowed COM references, event tokens, callbacks and deferrals separately.
- **Check COM contracts.** Verify interfaces against `WebView2.h` and the minimum supported Runtime. Feature-detect every interface newer than the base set; the slots M1 needs are listed in plan 3 ("Interface slots M1 needs") and checked by the slot-order test. Pair every subscription with its removal, and keep callbacks alive through late completions and shutdown.
- **Single instance first.** Enforce it before the environment exists. A second instance with different environment options fails at controller creation (`0x8007139F`, or `0x8000FFFF` when the first is exclusive): map both to a clear "another instance with different settings" error.
- **Shutdown follows plan 3** ("Teardown"), and starts only after the close request of the two-stage close is approved or skipped (designed at the start of M1b): mark closing, stop admitting calls and settle promises, keep pumping, check liveness before late replies, `Close` the controller on the STA. Exit without waiting for the browser. Wait for `BrowserProcessExited`, with a timeout, only before deleting or reusing a user data folder; it fires about 160 ms late and never after a failed controller creation (decision "Profiles and shutdown").
- **Failure recovery.** Handle `ProcessFailed` per view and `BrowserProcessExited` per environment, in either order; reset the affected call and stream state; no recovery during shutdown.
- **Heartbeat** (plan 3, "Hung pages"; built in `PageWatch`, rules in `Spar.Hosting.PageHeartbeat`): ping every 5 s, three misses mark the page unresponsive. The `ping` / `pong` bridge messages go to every document from its creation (`ContentLoading`, error pages excepted): the host's injected script (`PageScript.js`, added with `AddScriptToExecuteOnDocumentCreated` before the first `Navigate`) answers them, so a page that hangs before it connects the SDK is seen; never arm at `NavigationCompleted`, never on `hello`. Skip minimised, hidden and controller-hidden windows; keep one ping outstanding; treat `RenderProcessUnresponsive` and the alarm as one state with one dialog. "Reload page" terminates the renderer (pid from `GetProcessInfos`, STA only), then reloads once without using up the automatic reload. Never kill on its own, never replay a command. A close request pings first and gives the page one interval before "Wait / Close anyway".
- **Prompts the host takes down itself** (the hung-page dialog, the shutdown prompt) are task dialogs on an STA thread of their own (`PromptDialog`), dismissed with `TDM_CLICK_BUTTON`; the first button is the safe one and Esc chooses it. The hung-page dialog is owned by the window, whose thread keeps pumping. The shutdown prompt has no owner: the window may be gone, and a stuck owner thread would block the prompt (a dialog disables its owner through messages to the owner's thread).
- **Shutdown hang policy:** `ShutdownWatch` runs from the teardown's start until `Run` returns; after 10 s "Keep waiting / Exit now", again every 30 s; "Exit now" flushes the log and ends the process with exit code 10. No prompt in the automated mode.
- **The log** (M1b step 7; decision "Logging (implementation record; choices for review)"): `HostLog` opens the app's `app.log` (`Spar.Logging.LogFile`, the append-only handle every process of the app shares) at the host's first line, at the levels `SparLogging.Levels` reads before anything else (`spar.Logging`, then `logging.json` in the data root), and hands the same file to the services (`SparLogging.AddFile`, not owned), so the app's loggers and the host's lines share one writer. `HostLog.Logger` is one object for the run: stderr plus the file, then the app's factory once the services exist. Writing only queues (a bounded queue, drop and count); the file closes at process exit after the services, and "Exit now" closes it (2 s at most) before `TerminateProcess`. One process opens one `LogFile`; never a second writer beside it. The levels of `Program.cs` are a `Configure` of `LoggerFilterOptions` and those of `logging.json` a `PostConfigure` (`LogLevels.ApplyApp`, `ApplyFile`), so the file's level beats the app's own `"Default"` whatever the order of registration. The host takes its folders from `app.Builder.ResolveFolders()`, the value `Program.cs` may have resolved early; never compute them again.
- **Stall probe:** name every Spar callback on the UI thread with `UiThread.Enter` (window messages, WebView2 events, posted work); the probe exists only through `DiagnosticsOptions.CreateStallProbe` (the Development switch, or `KeepStallProbe()` in Production). Development-only triggers (`SPAR_DEV_PAGE_HANG`, `SPAR_DEV_UI_STALL_MS`, `SPAR_DEV_SLOW_DISPOSE_MS`, `SPAR_DEV_HEARTBEAT_MS`) are called only behind `SparDevelopment.IsSupported` at the call site, so the trimmer removes the class.

## Startup

- **Prerequisite checks, in plan 3's order as built:** OS build through `RtlGetVersion` (minimum Windows 10 22H2, build 19045), single instance, then `GetAvailableCoreWebView2BrowserVersionString` (never the registry), `CompareBrowserVersions` against Runtime 139, then normal start, where a controller creation failure means "broken". Exit codes are fixed for every app and the same on both OSes: 3 missing, 4 too old, 5 broken, 7 OS too old, 8 not responding, 9 another user, and 10 after "Exit now" at shutdown (plan 3, "Missing prerequisites"). The decisions are plain functions (`Prerequisites`), unit-tested; to force a path on a healthy machine use the Development-only overrides (`SPAR_DEV_REQUIRE_WEBVIEW2`, `SPAR_DEV_REQUIRE_WINDOWS_BUILD`) or a fake Runtime folder through `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER`, which only an app with `AllowBrowserEnvironmentOverrides()` honours (pitfall "The loader reads the Runtime's version"), never by uninstalling anything.
- **The message:** `TaskDialogIndirect`, which needs a Common Controls 6 and per-monitor DPI manifest, with `MessageBoxW` as fallback, on an STA thread of its own so the window's UI thread keeps pumping. The host opens links with `ShellExecuteW`. Write stderr when a handle exists (else the parent console) and the app's `app.log` always, from the log file's own task. The app's hook (`spar.OnStartupProblem`) may replace the dialog, never the exit code; it is not called in the automated mode.
- **Single instance:** the lock file and pipe of `SingleInstance`; never `PipeOptions.CurrentUserOnly`, and no `NamedPipeClientStream` or `WindowsIdentity` (image size): the client opens the pipe with `CreateFileW` and compares token user SIDs. Close the pipe when the teardown starts, release the lock at exit.
- **Window and readiness.** Show the window at once in the theme colour; never cloak it and never create the controller under a hidden parent, which does not render. Automation and headless runs use a shown, non-activated window placed offscreen, never `SW_HIDE` or minimized.
- **Theme without flicker (plan 3d):** a class brush plus a `WM_ERASEBKGND` handler, `DWMWA_USE_IMMERSIVE_DARK_MODE` before showing, the profile's `PreferredColorScheme`, and a transparent default background set at creation (`ControllerOptions3`, feature-detected). No `WEBVIEW2_DEFAULT_BACKGROUND_COLOR`.

## Serving, bridge and page security

- **One origin, every request answered.** Serve only the embedded frontend from `https://app.localhost`. Register the source-kinds filter (`ICoreWebView2_22`, all kinds) so workers are seen; answer unknown paths with 404 and foreign documents (`"*"`, `DOCUMENT`) with 403. Never answer with a redirect. The `MAP app.localhost ~NOTFOUND` resolver rule is defence in depth still to verify through the options object (plan 3, 3b).
- **Response headers on every response, worker scripts included:** `PagePolicy`'s headers, composed once off the UI thread from the generated catalog's declaration and the page's import-map hashes (`connect-src https://app.localhost`, because WebSockets bypass the host), `nosniff` with an exact `Content-Type`, `Cache-Control: no-store`, and the other headers in plan 3b; an HTML document gets its own policy with a fresh style nonce when the app asked for one. Always send `Permissions-Policy`: on Windows it is the only gate that held for the camera. Details in `spar-page-security`.
- **Serving assets.** `IStream::Read` runs on the UI thread and the response is read whole, so never block in it. The WebView never decodes `Content-Encoding`: the host decodes Brotli entries on a background thread at start and serves stored entries straight from the image (`GetManifestResourceStream` is an `UnmanagedMemoryStream` under NativeAOT; `SHCreateMemStream` copies anyway).
- **Guard the bridge.** Validate origin and frame before routing any message. Send strings only (`PostWebMessageAsString`, never `PostWebMessageAsJson`). Keep app-specific dispatch out of the native transport. A navigation starts a new document epoch (plan 2c): `NavigationStarting` closes the current session, and the new one opens at `ContentLoading`. Copy the message out on the STA; decode and admit it on the reader task.
- **Debug proxy** (decision "Debug serves Vite through the app's own origin"): Development-variant code only. `WebResourceRequested` takes a deferral, `HttpClient` (`UseProxy=false`, no automatic decompression) fetches from Vite, and the deferral completes on the STA. Forward `Accept` and `Sec-Fetch-*`, pass `Content-Type`, never cache, and drop `ETag` and `If-None-Match` for HTML.

## Production defaults (plan 3c)

- **Built in `BrowserDefaults`, `PageGuard`, `PagePicker` and `BrowserEnvironment`** (decision "Security defaults (implementation record; choices for review)"), each opted out only through `spar.Browser(b => …)`: devtools and Inspect off (`AreDevToolsEnabled`); accelerator keys off, and where devtools are on (Development, `AllowDevTools()`) the setting is on and `AcceleratorKeyPressed` sets `IsBrowserAcceleratorKeyEnabled = false` for every key but the devtools keys and, in Development, F5 and Ctrl+R; password autosave and general autofill off; swipe off and `NavigationStarting` back-or-forward cancelled (one borrow of `NavigationStartingEventArgs3`); host objects never allowed; `IsReputationCheckingRequired = false` (no route to other origins exists yet, so no override); `DownloadStarting` cancelled and handled; `ContextMenuRequested` keeps `cut`, `copy`, `paste`, `selectAll` in editable fields and `inspectElement` where devtools are on, and hides a menu left empty (and every menu in the automated mode). All set before the first navigation; an interface missing from the minimum Runtime fails the start (exit 4), never a start with the defaults off.
- **The page's pickers:** `Page.enable` then `Page.setInterceptFileChooserDialog` through `CallDevToolsProtocolMethod`, chained in one completion handler (no async machinery in Production), overlapping `AddScriptToExecuteOnDocumentCreated` and awaited before `Navigate`; `--disable-blink-features=FileSystemAccessLocal` in the environment options' `AdditionalBrowserArguments`. These two method names are the only DevTools Protocol use a Production image may carry: `Spar.BuildTests` refuses any other.
- **Image size:** a COM method the host calls costs about 300–420 B of stub and 120 B of metadata in the NativeAOT image. Keep getters that only feed a log line behind `SparDevelopment.IsSupported`, as `BrowserDefaults.Apply` does, and prefer Win32 calls through CsWin32 to BCL wrappers whose argument checks carry strings (`DriveInfo`, `Environment.SetEnvironmentVariable`).
- **Permissions:** deny anything the app did not declare; answer `PermissionRequested` explicitly and set `SavesInProfile = false` (plan 3b, "Permissions, two layers"; built in `PageGuard`, which feature-detects `ICoreWebView2PermissionRequestedEventArgs3`).
- **Interop size:** an interface the host only calls is declared with `Options = ComInterfaceOptions.ComObjectWrapper`; only the handler interfaces the host implements keep the managed-object wrapper (about 120 KB of the Notebook).
- **Environment overrides:** `BrowserEnvironment.Filter` removes the WebView2 variables (`BrowserEnvironment.Overrides()`, the four of plan 3c plus the channel and script-debugger names) with `SetEnvironmentVariableW` at the host's start, before the Runtime check (the loader's first call), unless the app calls `AllowBrowserEnvironmentOverrides()`; each is logged by name, never by value. That is enough: the loader reads them in-process and the browser inherits the block. Registry policies stay in force.
- Each default has an explicit C# opt-in, logged at startup and listed by `spar doctor`.

## Inspection

- Devtools and page automation exist only in Development and test builds and need an explicit session flag. Use in-process `CallDevToolsProtocolMethodAsync`; Spar never opens a remote debugging port (plan 3c, level 1). `AreDevToolsEnabled=false` only hides the browser UI and does not gate in-process CDP, so exclude automation at compile or trim time (a feature switch with `Trim="true"`), and prove the absence with the production boundary test.
- Before the first trusted input after a navigation, wait two animation frames; it can otherwise stall for 5 s.
- **Trusted input in a Development build:** `SPAR_DEV_INPUT` (`DevelopmentInput`, trimmed from Production) sends `Input.dispatchMouseEvent` and `Input.dispatchKeyEvent` steps after the first `ui-ready`. Mouse buttons, the back button and right clicks behave as real ones; key events never reach the browser's accelerators (F5 does not reload), so browser keys need real input (Windows Sandbox).
- **The page's console in a Development build** (`DevelopmentConsole`, M1b step 7 follow-up): `Runtime.enable` and the `Runtime.consoleAPICalled` event receiver (`GetDevToolsProtocolEventReceiver`, slot 42) on each WebView before its first navigation, behind `PageScript.ConsoleFromDevTools` (Development, not Test), so the injected script leaves `console.error` unwrapped and devtools' links stay the page's. On the UI thread only a quick look at the JSON (keys come sorted, `type` last) and a copy into a bounded queue; parsing, grouping and the per-document bounds run on its own task, which posts batches to `PageErrorLog` in the script's shape. Its handler is its own `[GeneratedComClass]`, never `WebView2EventHandler`, so Production carries none of it (the boundary test finds `Runtime.consoleAPICalled` and `Runtime.enable` in the host assembly and not in the image).

## Native services

- **Title bar drawn by the page** (plan 3, "Title bar drawn by the page"): windowed controller, `WS_OVERLAPPEDWINDOW` with the `WM_NCCALCSIZE` adjustment, `WM_NCHITTEST` from the page's cached layout (CSS pixels, scaled by the window's DPI), caption codes through one host-owned `WS_EX_TRANSPARENT` child above the WebView, the UIA provider with `ProviderOptions_RefuseNonClientSupport`, and the press kept across `WM_NCMOUSELEAVE`.
- **On the STA:** file dialogs (`IFileOpenDialog`, `IFileSaveDialog`) and `GetProcessInfos` (re-list on `ProcessInfosChanged`). Read process memory with kept handles on a pool thread.
- **Dialogs and focus:** JavaScript dialogs become the OS message box through a deferral. `beforeunload` never prompts.
- **The window's state reaches the controller only through the host** (built in `ViewWindowState`, M1b step 6): `WM_SETFOCUS` calls `MoveFocus(Programmatic)` (without it the keyboard reaches the page only after a click into it); a window activated while minimized gets focus on restore; a new controller (also after the browser is recreated) gets the window's visibility and, when the window has it, the focus. Never move focus while the window is disabled or not the active window: a dialog owns it then. `MoveFocusRequested` is handled and posts `MoveFocus` with its reason, so Tab cycles within the page. `WM_WINDOWPOSCHANGED` (return null, so `DefWindowProc` still sends `WM_SIZE` and `WM_MOVE`) sets `IsVisible` to shown and not minimized (a hidden window's page otherwise renders at full rate) and calls `NotifyParentWindowPositionChanged` on every move (or keyboard-opened popups appear at the old place). Don't resize the WebView to 0×0 while minimized. The earlier visible-window teardown mitigation is not used: the leak did not reproduce on Runtime 157 (pitfalls).
- **Tests with a tray icon** follow `AGENTS.md`: every icon leaves a per-user registry entry, so use Windows Sandbox or a fake (pitfall "notification-area icon").
- The decided APIs for each service are in plan 3 ("Native services") and `docs/app-model.md`; implement from the decided shape, not from the spikes' code.

## Loader, profiles and verification

- **Loader.** Under NativeAOT link `WebView2LoaderStatic.lib` (`DirectPInvoke` for `WebView2Loader` plus a `NativeLibrary` item, from `Microsoft.Web.WebView2` referenced with `ExcludeAssets="all" GeneratePathProperty="true"`). CoreCLR publications ship `WebView2Loader.dll`.
- **Profiles.** One user data folder per app, windows on the default profile. Shipped apps default to `%LOCALAPPDATA%\<Company>\<App>\WebView2`. In this repository pass a folder under `artifacts/webview2-profiles/`, never `%LOCALAPPDATA%`; tests use InPrivate. Clear data with `ClearBrowsingDataAll`, never `Profile8.Delete`, which poisons the name.
- **Verify on the real app.** Check startup, the affected native operations and shutdown on the published NativeAOT app, with an isolated profile, and that resources were released. Focus-dependent and real-input checks run in Windows Sandbox; checks that need the user go to the plan's table "Checks that need the user at the PC".
